## Finding 2: A suit pick cannot be treated as a plan for every compatible owned item
Recommendation: fix now

`.atelier/items/astromech-nnn0/item.md:30` assigns every matching saved pick to an item's row, while line 31 retains a shopping list costed once per pick and line 35 makes ADD TO PLAN act on the selected item. A single Night Vision pick consequently appears planned on every suit; a single Maverick grade 1-to-3 pick appears planned on two distinct grade-1 Mavericks. The shopping list still pays for only one installation or upgrade. This is a new false implication created by the loadout view, rather than the old generic recipe picker.

The existing contract confirms the mismatch: `app/src/lib/api/types/Pick.ts:3` has no owned-item identity; `app/src/lib/odyssey.ts:63` and `:94` identify and deduplicate picks solely by recipe; `crates/astromech-odyssey/src/shopping.rs:182` costs each pick once. The planned loadout reply in `.atelier/items/astromech-w1lj/item.md:27` exposes catalogue identity and gear facts, without requiring the journal's unique suit/weapon ID in each returned item.

Specify how a pick is assigned to one owned item before presenting it as that item's plan. Carry the unique ID through the loadout reply and preserve assignment and multiplicity when saving and costing plans, counting one item shared by several loadouts only once. Existing generic picks can remain unassigned until chosen. A smaller alternative is to show them only as compatible recipes, without claiming they are planned for each item. Cover two distinct compatible items and one item shared across loadouts in the acceptance tests.

## Finding 3: Refresh Now's cargo answer when its origin or sellable hold changes
Recommendation: fix now

`.atelier/items/astromech-coq6/item.md:37` refreshes the sale only on page open and a change in tonnes aboard. That leaves the default live page recommending the old nearby station with old jumps after a hyperspace jump carrying the same cargo. Switching to a different ship with the same cargo tonnage can also leave a station selected for the previous pad or range. Replacing cargo with an equal tonnage of another commodity between polls leaves the old commodity's sale total too.

These are actual inputs to the command: `crates/astromech-api/src/lookups.rs:377` resolves the current origin, range and filters and reads Cargo.json for each call; `crates/astromech-market/src/cargo.rs:263` searches from that origin and lines 267-268 calculate jumps from that position and range. The result does not update itself when those inputs change. `ShipStatus.sellable` already supplies the per-commodity quantities, so no new inventory command is needed.

Define a change key covering the sellable hold, current origin, and relevant ship/pad/range state. Use the existing local polls to detect changes and ask again only when the key changes, preserving the ban on unconditional timed network searches. Hide or mark the previous recommendation stale until the replacement arrives. Require behaviour cases for a jump with unchanged cargo and a changed hold with unchanged total tonnes.

## Finding 4: Identify a partial cargo sale beside Now's recommended total
Recommendation: fix now

`.atelier/items/astromech-coq6/item.md:32` calls `plan.stations[0].total` the best whole-load total and specifies its station, system, jumps and pad, but omits how much cargo that station takes. `crates/astromech-market/src/cargo.rs:116` caps each sale by demand, and lines 147-153 sum and rank those partial proceeds without requiring the station to take the whole hold. A top result can buy only 20 of 200 tonnes, or only one commodity of a mixed hold. The proposed dashboard presents that partial payout as what the hold would fetch and offers Set destination without disclosing the unsold cargo.

Keep the total, but require a visible quantity qualifier such as “takes 20 of 200 t” whenever it is partial, using `StationSale.sold` against the sellable load. The existing finder already carries this distinction in `app/src/lib/trade.ts:149`; the new summary must retain it. Include a partial-demand or mixed-hold result in the page's behaviour checks, and handle an empty `stations` list without a recommendation or destination action.
