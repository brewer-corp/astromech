## Finding 1: Adding a higher grade can retain two overlapping upgrades for the same item
Recommendation: fix now

`app/src/lib/suits.ts:79-84` handles a matching untied pick before consolidating an item's existing upgrade. With saved Maverick picks `{from:1,to:2,item:1700000000001}` and `{from:1,to:3}` (both `kind:"upgrade", gear:"maverick"`), select Explore's suit and ADD TO PLAN Grade 3. The loose-pick branch ties the second pick and returns immediately, leaving both 1-to-2 and 1-to-3 tied to that same suit. Reproduced through the page and in `addPick` directly. The row displays only Grade 3, and the panel's main cost takes the first upgrade, while the backend charges both: 3,450,000 cr and 9 Carbon Fibre Plating instead of 2,850,000 cr and 7. This violates both "Adding never doubles a plan" and the reported one-upgrade-per-item behavior. Consume the matching loose pick and merge the existing item upgrade in the same operation; cover the combination of an existing tied upgrade and a matching loose higher upgrade.

## Finding 2: Tying a lower upgrade silently reduces the item's existing target
Recommendation: fix now

`app/src/lib/suits.ts:82-92` replaces an existing upgrade's `to` with the incoming target unconditionally. Start with a tied Maverick 1-to-5 pick for `1700000000001` and an untied Maverick 1-to-3 pick. Under Not tied to an item, tie the latter to Explore/Raid's Maverick. The page saves a single 1-to-3 pick, losing the existing grade-5 plan. Reproduced with the actual Tie dropdown and directly with `tie`. Tying the loose plan should consolidate the overlap while preserving the higher planned target; reducing a target is not an action the commander requested. Retain the higher target when combining upgrades and add a regression case with the lower loose pick tied after the higher plan exists.

## Finding 3: Browser Back changes the loadout but leaves the previous item's panel active
Recommendation: fix now

`app/src/modules/suits/View.svelte:90-105` clears an incompatible `selId` only inside `chooseLoadout`; the hash listener changes `wantLoadout` without that reconciliation. Click Explore, click Spare, select Spare's Maverick Suit, then use browser Back. The heading and rows return to Explore, whose suit has the recorded Grade 3 and Night Vision plan, but the panel still describes Spare's different grade-1 Maverick and says No plan. No visible loadout row is selected, yet ADD TO PLAN still targets Spare's item. Reproduced in the running preview. Reconcile panel selection whenever the effective loadout changes, including hash/history navigation and a worn-loadout change from refreshed journal data; retain the panel only when the new loadout contains that same item. Cover Back between the two Maverick loadouts.
