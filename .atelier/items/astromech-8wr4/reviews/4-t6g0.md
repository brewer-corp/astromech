## Finding 1: Drive the adapted engineer-refresh test with fake timers
Recommendation: fix now

In app/src/modules/engineering/Build.browser.test.ts:296–305, the test adapted to render the new page changes the preview's engineer-poll answer and waits up to 2500 ms for failure, then changes it back and waits another 2500 ms for recovery. It never installs or advances fake timers, so both transitions depend on the real setInterval(tick, 1000) in Build.svelte. The focused verbose run passed, but this case took 2008 ms because it waited for both real polls.

This timing pattern was inherited from the old test, but the case is modified by this change. CONTRIBUTING.md's Tests rules explicitly apply to any test changed and require timer-driven code to use fake timers. The full suite passing does not remove that scheduling dependency.

Install vi.useFakeTimers({ toFake: ["setInterval", "clearInterval"] }) before rendering, advance the clock by 1000 ms after changing the answer to failure, then advance it again after restoring success. Keep the assertions that the trip remains visible and the stale message clears. View.browser.test.ts's empty-fleet refresh case now demonstrates the required pattern. No production change or wider timeout is needed.
