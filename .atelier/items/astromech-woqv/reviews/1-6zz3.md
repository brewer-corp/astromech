## Finding 1: Read the current NavRoute for the timeline at startup
Recommendation: fix now

`crates/astromech-core/src/route.rs:820-823` populates the timeline's new `Saved::nav` only through `Desk::plotted`. That callback only runs for a live route input: `RouteFollow::replayed` handles journal arrivals but ignores `Input::Route` (`crates/astromech-announce/src/route_follow.rs:107-110`). At startup, `pipeline::on_companions` loads NavRoute into GameState with the engine set to replay, and `Engine::route` then remembers that snapshot and suppresses subsequent identical reads. Consequently, a route already plotted when astromech launches never supplies the timeline's jumps, star classes or position. A persisted `nav` can also remain stale if the galaxy-map route changed while astromech was stopped.

Reproduction: seed a temporary copy of `worlds/preview/route/game` with the fixture world's 12-system NavRoute, start the core, follow `fixtures/route.json`'s plotted neutron route through `route_set`, and step through an identical NavRoute file/journal update. With `here = Sol` and next stop `PSR J1752-2806`, `route` returns `hops = null` and `position = null`. With the same world and calls, but the NavRoute file first appearing after startup, it returns 11 hops and position 0. The file ends at the next stop in both cases, so this violates the required NavRoute precedence.

Synchronize the timeline with the current GameState/NavRoute snapshot independently of live follower actions. Reading startup data must not advance the followed route or write the clipboard. Add a regression case for an existing startup NavRoute and replacement of a stale saved snapshot.

## Finding 2: Preserve successful stop batches when another batch fails
Recommendation: fix now

`crates/astromech-galaxy/src/stops.rs:31-35` returns immediately on any failed chunk and discards the `out` accumulated from earlier successful requests. Meanwhile, `Desk::take_details_wanted` has already marked every stop as looked up (`crates/astromech-core/src/route.rs:675-682`), and `Core::route_details` only stores results on an overall `Ok` (`crates/astromech-core/src/app.rs:1026-1030`). One failed request therefore erases successful results and permanently suppresses requests for all later chunks, including stops never attempted. This goes beyond leaving the failed lookup's stops without details.

Reproduction: follow the first 51 distinct systems of the recorded full Sol-Colonia neutron route, answer the first systems-search request with the recorded `spansh-route-stops.json` response, and answer the second with HTTP 503. `route_details` returns Sol with `details = null`, although the first response supplied its population and faction details. Fetching the first 50 stops before adding stop 51, with the same two responses, preserves Sol's complete details. A route over 100 stops additionally leaves later chunks unattempted and ineligible for another call.

Handle failures per chunk, retain successful results, and continue looking up the remaining chunks. Keep the intended once-per-stop behavior for chunks actually attempted. Add a case with a successful chunk, a failed chunk, and a later chunk to cover both lost results and skipped requests.
