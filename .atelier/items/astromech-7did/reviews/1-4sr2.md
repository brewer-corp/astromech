## Finding 1: Choose the nearest engineer when today's available grades tie
Recommendation: fix now

`crates/astromech-engineering/src/search.rs:341-346` sorts by `best` before distance even when `today` is equal. That violates Done when 3's rule: highest grade available at the commander's current rank, nearest first. An eventual higher grade is not available today and must not win this tie.

The production-search probe, using the preview world's Shinrarta Dezhra position, unlocked Farseer and Palin at rank 3. Both return `today = 3`, but the main answer is Farseer at 101.77 ly (`best = 5`), ahead of Palin at 41.10 ly (`best = 3`). The Report and guide promise Palin in this situation. Select today's main answer by descending `today`, then distance, and add a regression for unequal eventual grades with equal available grades.

## Finding 2: Barred high-grade engineers can hide an available unlock answer
Recommendation: fix now

`crates/astromech-engineering/src/search.rs:348-353` decides whether to run the unlock selection from the first row after sorting by eventual grade. If that row is barred, it sets `main = None` and never searches the other rows for a usable unlock candidate.

With The Sarge and Marsha Hicks barred and all other progress left as in the preview world, production `search("cannon", ...)` returns `main = None`: those two grade-5 engineers sort before the still-Known Tod McQuinn, who offers grade 2 and has an invitation step. Search.svelte therefore renders no main answer, although Done when 3 requires the nearest engineer to unlock when none is unlocked. Select the unlock candidate across non-barred hits; return no main answer only if no eligible candidate exists. Cover this case separately from the all-barred case.

## Finding 3: Preserve uncertainty on suit modification offers
Recommendation: fix now

`crates/astromech-api/src/commands.rs:147-153` reduces Odyssey offers to modification names and discards `Engineer.unconfirmed_mods`. `SearchHit.mods` and `Search.svelte` consequently present disputed offers as certain, including in the primary recommendation once that engineer is unlocked.

This already occurs in the committed `range` fixture. On the real preview world, `odyssey_view` returns Rosa Dayette's Greater Range with `unconfirmed: true`, while `engineering_search {query: "range"}` returns only `mods: ["Greater Range"]`. The existing Engineers tree deliberately marks this same offer `(?)` and explains that the wiki disagrees. The new search loses that warning beside actions that send the commander there. Carry the existing uncertainty information through the search reply and show the same qualification in its rows and main answer. A recorded-reply regression can use Rosa's existing range offer.

## Finding 4: A new query keeps the previous query's destination actions active
Recommendation: fix now

`app/src/modules/unlocks/View.svelte:71-80` keeps `found` unchanged while the next search is pending, and `:132-133` renders it without checking that it belongs to the current query. Only the summary beside the box has a query-equality guard. There is no pending indication, dimming or protection on the old destination actions.

An event-controlled browser test reproduced this with the recorded replies: search FSD, type laser, hold the laser response at the transport boundary. The box and URL now say laser, but the main answer still names Farseer and its Set destination button remains enabled, even though Farseer does not engineer lasers. The request counter prevents out-of-order replies from replacing newer replies; it does not prevent this stale answer from being presented as current. Track the pending query and distinguish its old results from the new answer. Show a loading line and prevent the old route actions from being mistaken for actions on the new query. Add a browser regression using a deferred transport response, without a sleep.
